## Why would an edge be negative?

Most edge weights are costs: kilometres, minutes, euros. But sometimes using an edge *pays you back*, and then its weight is negative:

- **Money.** A route with a toll refund, or a trade that earns more than it costs. In currency exchange, a loop of trades that comes back with more money than it started with is called arbitrage.
- **Energy.** An electric car *gains* charge going downhill, thanks to regenerative braking.
- **Games.** A path through a treasure cave earns gold. A healing spring restores stamina.
- **Hidden inside other problems.** Scheduling rules like "task A must start at least 3 minutes after task B", and many network-flow algorithms, boil down to shortest paths with negative edges.

Negative edges bring a new danger. If a loop of edges adds up to less than zero (a <Term id="negative-cycle">negative cycle</Term>), you can go round it forever and keep getting cheaper:

With a negative cycle, "shortest route" simply has no answer. So the real task is: **find the shortest distances when some edges are negative, or prove there is a negative cycle and point to it.**

## Bellman–Ford: correct but slow

The classic safe choice is the Bellman–Ford algorithm (1955–58). It doesn't try to be clever about order. It simply relaxes **every** edge, then does it again, and again:

- After round 1, every vertex whose best route has 1 edge has the right distance. After round 2, every vertex whose best route has up to 2 edges does, and so on.
- A shortest route never needs more than n − 1 edges, so **n − 1 rounds** are always enough.
- If one extra round *still* improves something, distances can drop forever: there is a negative cycle.

<BellmanFordFigure
  number="2.3"
  tryThis={<p>Run it once as it is: it gets the distances Dijkstra missed. Then lower the weight of C → B to 2 or less, which makes the loop B → A → C → B negative, and run it again. Bellman–Ford finds the cycle.</p>}
/>

The price is speed. Every round touches all m edges, and there can be n − 1 rounds, so the total work is about **n × m**. On a graph with a million vertices, that is up to a million passes over every edge, where Dijkstra needs one.

<DeepDive title="Why n − 1 rounds always suffice">

Take any vertex v and a shortest route s → x₁ → x₂ → … → v with k edges. Without negative cycles we can assume the route visits no vertex twice, so k ≤ n − 1. Round 1 relaxes the edge s → x₁, so x₁ is correct after round 1. Round 2 relaxes x₁ → x₂ while x₁ is already correct, and so on. After round k, v is correct. With n vertices, k is at most n − 1.

This is also why a change in round n proves a negative cycle: no correct distance can still improve, so some "shortest" route must keep getting shorter, which only a negative loop allows.

For *integer* weights, scaling algorithms (Gabow and Tarjan 1989; Goldberg 1995) improved this to about m√n · log W. For general real-number weights, nobody beat n × m until 2024.

</DeepDive>

## Potentials: changing the weights without changing the answer

Here is the key tool behind the 2022 breakthrough, and it is older than you might think. Give every vertex a number, its **height** (also called a <Term id="potential">potential</Term> or price). Then replace every edge's weight like this:

<Callout title="Reweighting with heights">

**new weight of u → v = old weight + height(u) − height(v)**

</Callout>

Now add up the new weights along any route from S to T. Every vertex in the middle of the route has its height added once (leaving it) and subtracted once (arriving), so those cancel. Only the ends survive:

**new route length = old route length + height(S) − height(T)**

*Every* route from S to T changes by the same amount, so the shortest route stays the shortest. If we can choose heights that make **every edge non-negative**, plain Dijkstra works again. Try it:

<PotentialsFigure
  number="2.4"
  tryThis={<p>Make every edge non-negative. Start with the red edge A → B (−2): raise A or lower B until it reaches 0. Watch the table: whatever you do, all five routes move up or down together, and S → A → B → C → T stays the shortest. Stuck? Press "Show a solution".</p>}
/>

<Callout title="You've seen this trick before: it's A*">

If you've written game pathfinding with <Term id="a-star">A*</Term>, you've used potentials. A* is exactly Dijkstra on edges reweighted by its heuristic h: height = −h(v). A heuristic is called *consistent* when every reweighted edge is non-negative, which is precisely the condition that makes Dijkstra correct.

</Callout>

There's a catch, though. The heights behind "Show a solution" come from Johnson's 1977 recipe: take the shortest distances from an extra vertex connected to everything by 0-weight edges. Those distances always make every edge non-negative. But computing them *is* a negative-weight shortest-path problem, the very thing we were trying to solve. Potentials turn the question into **how to find good heights cheaply**.

## A faster engine: Dijkstra plus Bellman–Ford

One more ingredient. What if we run Dijkstra but *ignore* the negative edges, then do a single Bellman–Ford pass over just the negative edges, and repeat?

1. **Dijkstra pass:** take queued vertices smallest-first and relax their non-negative edges, like Chapter 1.
2. **Bellman–Ford pass:** relax the negative edges out of every vertex the Dijkstra pass just handled.
3. Any vertex that improved goes back into the queue for the next round. Stop when nothing improves.

Each round fixes every vertex whose best route uses one more negative edge. So if every shortest route uses at most <Term id="eta">η</Term> negative edges, this hybrid finishes within **η + 1 rounds**, and each round is only about as expensive as Dijkstra.

<Callout title="The key idea of this chapter">

The hybrid is fast when **η is small**, meaning when shortest routes pass through only a few negative edges. Potentials can change which edges are negative without changing any answer. So the question becomes: can we find heights that leave shortest routes with *few* negative edges, without first solving the whole problem? In 2022, the answer turned out to be yes.

</Callout>

<DeepDive title="How fast is the hybrid, exactly?">

Each round is one Dijkstra pass (about m + n log n work) plus one pass over the negative edges, so the total is roughly (η + 1) × (m + n log n). A sharper count, used in the 2022 paper (where the hybrid is called *ElimNeg*), charges each vertex only for the rounds it actually changes in. That gives about log n × (n + the sum of η(v) over all vertices v).

If a negative cycle exists, the rounds would never stop. But without one, η is at most n − 1, so this demo declares a negative cycle as soon as round n + 1 would begin.

</DeepDive>

## The 2022 breakthrough: make η small

In 2022, Aaron Bernstein, Danupon Nanongkai and Christian Wulff-Nilsen showed how to find good heights almost as fast as running Dijkstra once. Their paper won the best paper award at FOCS, one of the two top conferences in theoretical computer science. What surprised people was that it needs no heavy machinery, just the tools from this chapter combined in a clever way. One pass of their method has four phases:

1. **Cluster.** Pretend for a moment that negative edges cost 0, and carve the graph into *clusters*: groups of vertices that are all close to each other. The carving uses balls of *random* size around random vertices. That randomness is what keeps cuts rare: a short edge is unlikely to sit exactly where a random ball happens to end.
2. **Fix the inside of each cluster**, by running the same method on each cluster alone. This is recursion, and it works because a tight cluster can't hide many negative edges on one route (see the deep dive below).
3. **Fix the edges between clusters.** The uncut edges between clusters never loop back, so the clusters can be put in order. Then one sweep lowers each cluster's heights just enough to make every forward edge non-negative.
4. **Clean up.** Only the few *cut* edges can still be negative, so shortest routes contain few of them, and the hybrid from Section 2.5 finishes in a few rounds.

**Scaling** ties it together. The clustering argument only works when negative edges are *slightly* negative. So the real algorithm multiplies every weight by 2n and runs the pass in rounds:

- The first round makes every edge at least −B/2, the next at least −B/4, and so on, for about log(nW) rounds.
- Each round is one call of the method above (called *ScaleDown* in the paper), and each call halves how negative any edge may be.
- Once every edge is at least −1, adding 1 to every edge makes them all non-negative. Because of the factor 2n, adding 1 per edge can't change which route is shortest. One run of Dijkstra finishes the job.

The result runs in **O(m log⁸ n · log W)** time, where W is the size of the most negative weight. That is near-linear: m times a handful of log factors, which come from the scaling rounds, the recursion depth, the random cutting and Dijkstra's priority queue. The algorithm is randomized, but in its full form it never gives a wrong answer: the randomness only affects how long it takes. It also handles negative cycles. If one exists, the clean-up could keep improving distances forever, so the full algorithm watches for that and returns the cycle instead.

<DeepDive title="Why a tight cluster can't hide many negative edges">

Take one ScaleDown round, where every edge is at least −2B. The method first adds B to each negative edge, so they become at least −B, and it treats them as 0 while clustering. Every cluster is then "tight": any vertex in it can reach any other within distance about D = (Δ/2) · B, where Δ is the current limit on how many negative edges a shortest route may need.

Now suppose a shortest route *inside* a cluster used more than Δ/2 negative edges. Each subtracts close to B, so its total would drop below about −(Δ/2) · B. But tightness means you can walk from the route's end back to its start for at most about (Δ/2) · B. Together that is a loop with negative total weight, a negative cycle. So without negative cycles, routes inside a cluster need at most Δ/2 negative edges. The recursive call works with Δ/2, half the previous limit, and after about log n levels the limit is small enough to finish directly.

For the edges that were cut, the randomness does the work. An edge of length ℓ is cut with probability about ℓ · log² n / D, so a shortest route contains only O(log² n) cut edges on average, and the clean-up's hybrid needs only that many rounds.

</DeepDive>

## What happened next

The 2022 paper opened the floodgates. About a year later, Bringmann, Cassis and Fischer removed almost six of the log factors. Later work sped up the clustering step itself. And in 2025, an engineered implementation turned out to be up to almost 100× faster than the classic method on the hardest test graphs. So unlike many theory results, this one looks practical.

There is also a harder version of the problem: weights that are arbitrary real numbers, where the running time may not depend on how big the numbers are. There, nobody had beaten Bellman–Ford's n × m since the 1950s, until Jeremy Fineman did in 2024. Since then the bound has kept falling, and a July 2026 preprint claims almost-linear time for this version too.
